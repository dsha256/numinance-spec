# RFC-0003: the evidence chain and export format, evidence/v1

- Status: open (acceptance follows the reviews of the change that adds it)
- Author: the project maintainers
- Opened: 2026-11-02
- Change class: contract-additive (documents the shipped format; no format change)

## Problem
Every export is required to verify offline with `numi evidence verify`. The canonical form, the record hash, the chain rules, the Merkle and checkpoint rules and the bundle layout exist only as code in the private tree. An auditor who must run our private binary is not independent, and the public specification tree must never import it. A project ruling owed this RFC, with golden vectors, before any external export, and the evidence decision record decided where it lives.

## Proposal
Publish the shipped format as `evidence/v1`, spec version 1.0.0, with no change to it:

- Prose specification in `numinance-spec/docs/evidence/`: canonical form and strict decoding; the record, its validity rules and the per-change chain with terminal and seal records; log leaves, RFC 6962 hashing, inclusion proofs and checkpoints; the bundle layout, index, design list and absent parts; the attestation and the signed bundle manifest; every derivation a verifier re-derives; finding codes, result levels with their precedence, key modes, exit codes, reports and trust limits.
- JSON Schemas in `numinance-spec/schemas/evidence/v1/`, checked in CI with the repository's own schema validator against every verifying golden export.
- Conformance vectors in `numinance-spec/conformance/evidence/v1/`: golden export directories generated by a private deterministic test, signed only with generated test keys, each with an `expected.json` (exit code, level, finding codes, flags, key files). At least one negative vector exists for every finding code of the shipped verifier (one code, `too_many_records`, cannot ship as data and is listed with the reason), and for every result level, every key mode, every allow flag alone and combined, truncation with and without each allow flag, wrong and absent log proofs, an attestation gap, the canonical-form edge cases, links and size bounds. The private test runs the shipped `numi evidence verify` over every shipped vector and asserts `expected.json`, so the vectors are proven against the shipped code today; the open verifier will run the same data, and the private verifier claims parity only when both agree on every vector.
- The attestation field types are as shipped in `attestation.proto`: `ticket` a string (`<reference>#sha256:<hex>` or `none`), `credential_scopes` a repeated string (`broker.scopes.v1 sha256:<hex>` then sorted handle lines, each entry printable ASCII of at most 256 bytes), `network_policy` a `Reference` whose `ref` is `egress-policy.v1/<change id>` of the attestation's own change. A richer shape is a separate proposal.

Two behaviours are specified here as NEW, because the shipped verifier does not have them and the ADR asks this step to define them: a `--json` report with `level_enum`, `weakened_by_flags` and `anchored_head_record_hash`, so automation can tell an allowance-bearing pass (which still exits 0) from a plain pass; and the flags `--expect-change` and `--expect-head`, with a mismatch exiting 3 under a new finding code `expectation_mismatch`. The any-pinned-key-may-sign rule of a repeatable `--runner-key` is the shipped behaviour, stated. The NEW behaviours are additive on a report and on a command line, and the vectors that carry them have status `target`.

## Alternatives
- Move the canon into `numinance-spec` and import it privately: one shared implementation makes parity meaningless.
- Spec without vectors: the vectors are what keep two implementations aligned.
- Change the format first (JCS, a stronger anchor, key roles): a contract-breaking proposal with its own ADR and a major version. Nothing found while writing this spec requires it (see the findings below).

## Compatibility and migration
No behaviour changes. The spec freezes today's bytes as `evidence/v1`. Later changes are additive (a new optional key with a `since`, a new finding code, a new vector) or a new major. A verifier of `evidence/v1` refuses a document with a key it does not know, so an additive key is a minor of the spec and of the schema, never silent.

## Security considerations
The spec states its trust limits (`docs/evidence/verification.md` section 9): keys and log pins come only from the caller; there is no key rotation, revocation or per-role separation in v1; a customer who holds the runner key and the log key can equivocate; an unsigned export's truncation is detected only with a pinned log; the leaf fields are the runner's statements. The vectors include the attacks the verifier is meant to catch (a forged or reordered record, a truncated chain with its summary and index rewritten, a wholesale replacement, a wrong or absent log proof, a manifest signed by another key, a non-canonical record form) and the cases where a flag makes a pass weaker, so that its level says so. The release ordering rule of the evidence ADR is restated unchanged (`docs/evidence/verification.md` section 10) and is not loosened by this RFC.

## Findings recorded, not chosen
Writing the spec against the shipped code found the following. None was changed here. Each is stated in the spec as the shipped behaviour, and the vectors pin it.

1. `bundle_manifest.proto` says the manifest holds at most 4096 entries. The shipped decoders bound the manifest, the index and the directory at 64, and the effective limit is lower: every manifest path is a known file name, not the manifest, and unique after lowercasing (at most 15), and an index lists no manifest and no index (at most 14). The spec states the shipped bounds. The proto comment is corrected by a separate `docs` change, or the bound is raised in code under its own change; this RFC does not choose.
2. The printable-text rule of `executor_id`, `model_id` and the checkpoint origin is Go's `unicode.IsPrint`, so the accepted set depends on the Unicode table of the Go release that builds the verifier. A verifier in another language, or a later Go release that assigns more code points, can disagree on a newly assigned character. The vectors cover three code points no release treats as printable. A portable rule (a listed table version, or a restriction to a named set) would be a later, additive change.
3. The canonical string form is what `encoding/json` of the Go release writes. Backspace and form feed are short escapes since Go 1.22, and the rule that escaped HTML characters are written raw is a repository choice. Evidence strings cannot hold control characters except an absent-part reason of the index, which the vectors exercise (positive and negative forms). A Go release that changes an escape would change those bytes.
4. The shipped tool-events reader finds `seq` with Go's JSON decoding of a line: the key is matched without regard to case and the last value of a repeated key wins; no other part of a line is inspected. The digest the chain cites binds the bytes, so the effect is limited to where a stream is split. The spec requires the same reading, and two vectors carry it.
5. Anchor files are not decoded when no log is pinned: garbage in them is accepted and reported as not anchored, and only the pair rule and the manifest's digest of the checkpoint apply. The level always says so.
6. The `size` of an index or manifest entry, and `records` and `denied` of a summary, decode as unsigned 64-bit integers without the 2^53-1 bound that other counters have; such a value can never equal a real size or count, so it fails as a mismatch.
7. A Closed change with an attestation gap is never fully anchored (there is no attestation or manifest to prove).
8. When the index does not decode, no file is hashed by the index step, so the manifest cannot match any of its entries and reports a mismatch beside `index_invalid`.

No finding changes a hash, a signature or a canonical byte of a format that exists, so none needs a contract-breaking change now.

## Open questions
- Whether the log pin should also admit a witnessed checkpoint form. Not in `evidence/v1`.
- Whether finding 2 is closed by pinning a Unicode table version in a later minor.
