# Trajectory statements

Status: normative for `evidence/v1` (spec 1.0.0). Read [records and chain](records-and-chain.md) and [receipts](receipts.md) first.

An executor's event stream is trajectory: what the agent reports it did. It is stored as an artifact and is not evidence of record. Evidence of record comes from the receipts the trusted components produce. Where the two overlap, the runner compares them before the change ends, and states the result as a record of the chain, so a mismatch is a finding and not a silent difference.

## 1. Shape

A trajectory statement has the action `TrajectoryCompared.v1`, `actor_kind` `runner`, outcome `succeeded`, no `lifecycle` and no `corrects_record_hash`. A change has at most one, and its `ev_id` is `ev_` and the first 32 hex digits of the sha256 of `numinance.trajectory.v1`, a line feed and the change id, so a retry of the write is the same record. It is written after the components' last receipts and before the terminal record, so it is inside the range the attestation covers. A change with no executor stream has none: there is no trajectory to compare, and a chain without the statement is valid. `canon_version` is unchanged.

| Part | Content |
|---|---|
| `inputs` | `trajectory/stream/<i>` then `trajectory/candidate/<i>`, each numbered from 0 in order, `sha256` the digest of the stream or of the candidate tar that was read |
| `outputs` | markers `trajectory/<key>/<value>` whose `sha256` is the digest of the ref text, in this order: `result` (`corroborated`, `mismatch` or `unverifiable`); `reason` only when the result is `unverifiable` (see section 3); then the counts `runs`, `files_reported`, `files_recorded`, `files_unrecorded`, `files_unreported`, `network_reported`, `network_recorded`, `network_unrecorded`, `network_unreported`, `commands_reported`, each a canonical non-negative integer of at most 1048576 |

At most 64 streams and 64 candidates are cited. The result and the counts agree: `corroborated` has no discrepancy (`files_unrecorded`, `files_unreported`, `network_unrecorded` and `network_unreported` all zero), `mismatch` has at least one, `unverifiable` has a reason. The record holds counts and closed tokens only: never a path, a host, a tool name, tool output or free text. The two directions of each comparison are separate counts.

## 2. What is compared

The comparison reads the canonical event types of the stream only (design section 11): an executor maps its own tools to those types, and the statement names no vendor tool. It reads chain records only.

- Files, for each run whose `execution.stream` record is `succeeded`. The distinct paths of the stream's `FILE_CHANGED` events against the distinct paths of the manifest of the candidate that run's own `execution.diff` record digests (never the sum over several runs). A reported path the candidate does not hold counts in `files_unrecorded`; a candidate path never reported counts in `files_unreported`. A completed run with no `execution.diff` record has an empty candidate. Known false positives: a file the agent changed and then restored is reported and not in the candidate; a candidate that already holds an earlier run's paths shows them as unreported.
- Network, across the streams of every run of the change. The streams' `NETWORK_REQUEST` events (`network_reported`) against the request lines of the egress proxy's receipts, allowed or denied, that are not explained by the chain (`network_recorded`): a line that presented a handle issued for the executor's inference intent is not counted, and neither is a line of a handle the broker issued for an invocation that a record of the host's own capability call cites as an `invocation/<id>` input (for example the SCM provider's requests of `scm.open_pull_request`; `execution.stream`, `execution.diff`, lifecycle and receipt records never explain a line); a line is attributed by the fields of [receipts](receipts.md) only (its handle ref). A request the proxy denied matches a request the agent reported. The canonical event has no host, so the match is of presence: lines on one side and none on the other is the discrepancy (`network_unrecorded` or `network_unreported`), and nothing of a host enters the statement. Residuals: an invocation of the plugin host with no record on the chain, a host push (its record cites no invocation id), a record of the executor port (`authorexecutor.*`), which never explains a line, and harness traffic that presents no inference handle, are counted as requests the agent did not report; a tool that a server runs for the executor leaves no proxy line and is reported by no event. When a component's receipts are known incomplete (it restarted, the chain hit its bound, or the producer had no source of receipts) the network side is not judged.
- Commands. `COMMAND_EXECUTED` events are counted in `commands_reported` and never compared: no trusted component records a command.

## 3. Reasons and what a verifier does

`unverifiable` carries one reason. `stream_unreadable` (a stream the chain cites is not held, or is not its digest) and `stream_malformed` (outside the closed grammar or the size limits) are caused by the trajectory stream. `candidate_unreadable` and `candidate_malformed` are about the candidate the host made, `receipts_incomplete` about the components' receipts, and `too_many_runs` says the chain holds more than 64 runs.

A record with this action and any other `actor_kind`, outcome, input or output than above is `record_invalid`. A verifier checks the shape of the record, that the cited digests are well formed, that the `ev_id` is the derived one, that the chain holds at most one statement and that it precedes the terminal record (`chain_broken` otherwise). It does not recompute the comparison and does not recompute the file set. It reports the result (`trajectory` in the JSON report, a `trajectory:` line in the text); a `mismatch` or `unverifiable` result is a finding to read, never a failure of the export.

What the statement proves is what the runner signed. A trajectory the runner could not read or that is outside its grammar or size limits is `unverifiable`, never `corroborated`. The producer signs the attestation over a `mismatch` and over an `unverifiable` result whose reason is a stream reason: the statement is inside the sequence range the attestation binds. Only an `unverifiable` result on the trusted side (`candidate_unreadable`, `candidate_malformed`, `receipts_incomplete`, `too_many_runs`) makes the producer record an attestation gap, which a verifier reads as an incomplete export.
