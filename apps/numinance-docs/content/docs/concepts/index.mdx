<ShortProductTruth>
Give it context. Let it engineer. Your policy decides, not the model, and the evidence lets you check the result.
</ShortProductTruth>

Numinance treats intelligence as one component of an engineering system. Context, authority, execution, verification and evidence are separate boundaries, each with a contract you can read. These ten pages build that model in order. Read them once, then use the architecture, configuration and protocol sections as reference.

## The model in one pass

```text
objective -> context -> understand -> plan -> act -> verify -> evidence
                              |                    |
                  policy decides before every privileged action
```

## The invariants

These hold across every page. If a page seems to weaken one, treat it as a documentation bug.

1. Policy is evaluated outside the model before every privileged action.
2. Authority is expressed as capability-based grants, bounded by scope, risk, environment and expiry.
3. Four identities are distinct: author-agent, reviewer-agent, release-pipeline and human approver. No identity approves its own work, and only the release-pipeline deploys.
4. Evidence is append-only, written by the runner identity, and denials are recorded too.
5. Protected paths cannot be changed by an agent.
6. Extensions are signed, digest-pinned and declare their permissions.
7. A customer-local circuit breaker can stop or downgrade the system.
8. Orchestration payloads carry references and digests, never content.
9. Break-glass is human-only.

<Callout type="warn" title="Designed versus available">
Most of the runtime behavior in this section is designed and lives in the proprietary engine. What you can run today is the open `numi` CLI for schema validation and evidence verification. Check the [status page](/docs/status) before relying on any capability.
</Callout>
