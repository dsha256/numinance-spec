<ShortProductTruth>Guides follow a job to be done, not a module. Each one says up front whether you can run it today with the open `numi` CLI or whether it is a designed walkthrough of the proprietary engine.</ShortProductTruth>

<FeatureStatus kind="public-spec">
Guides marked "Runnable today" use only the open `numi` CLI, the numinance-spec repository and its SDKs. Guides marked "Designed walkthrough" describe the Numinance engine, which is proprietary and not generally available. Installing `numi` does not install an autonomous engineer.
</FeatureStatus>

## How to read the executability labels

| Label | Meaning | What you need |
| --- | --- | --- |
| Runnable today | Every command in the guide exists in the open build and was run to produce the output shown. | A clone of the spec repository and the Go toolchain. See [Install](/docs/get-started/install). |
| Partly runnable | The configuration and checks are real and runnable; the live behaviour they configure belongs to the engine. | Same as above. The guide marks where it stops. |
| Designed walkthrough | A storyboard of the engine, tied to real configuration documents. There is no runnable engine command. | Nothing to run. Read it to learn what you would configure and what you would approve. |

The open build validates documents (`numi validate --files`), generates a starting configuration (`numi init`) and verifies evidence offline (`numi evidence verify`). Running a change, exporting evidence, tripping the breaker and approving a gate are engine features. See [Status](/docs/status) for the full matrix.

## Suggested order

<Steps>
<Step>

### Get a configuration on disk

Start with [Onboard a repository](/docs/guides/onboard-repository). It is the only guide that produces files you keep: five documents under `.numinance/policy/` that name your toolchain, playbook, stage registry and autonomy level.

</Step>
<Step>

### Decide how far the agent may go

[Choose an autonomy level](/docs/guides/choose-autonomy) turns the ladder into a policy. The shipped starting point is the pull-request level. Raising it is a policy change that a human reviews, not something an agent can ask for.

</Step>
<Step>

### Wire in your systems and your own capabilities

[Connect source control and CI](/docs/guides/connect-source-control-and-ci), [Connect knowledge](/docs/guides/connect-knowledge) and [Build a custom plugin](/docs/guides/build-custom-plugin) cover the provider side of the contract.

</Step>
<Step>

### Read the storyboards, then check the evidence

The three change-type guides show what the engine is designed to do with that configuration. [Verify a run](/docs/guides/verify-a-run) shows how you check the outcome without trusting the engine that produced it.

</Step>
</Steps>

<Callout type="info" title="One pass through the rules">
Every guide inherits the same invariants: policy is evaluated outside the model before every privileged action, the author and reviewer agents cannot approve their own work, only the release pipeline deploys, and evidence is written by the runner. "Your policy decides. Not the model."
</Callout>
