<ShortProductTruth>A conformance pass states compatibility with the spec at a version. It is not a security certification, not an endorsement, and not a claim about any provider's behavior against a live system.</ShortProductTruth>

## When to use this

Use the kits while writing a provider to find contract mistakes early, and as the evidence a registry or a customer can ask for. A manifest names its kit in `conformance_suite` (`conformance/<port>/<major>/<suite>`); the host looks it up in its own index and runs it, and never trusts the claim.

## How the kits are organised

Each port has `conformance/<port>/v1/`. The version tracks the port minor. Most directories contain a README with the case table, and the runnable ones add a Go package `kit.go` plus `kit_test.go`.

Every README has the same three parts:

- **Core** cases (`CORE-nnn`) that test the provider through the port's verbs.
- **Host checks** (`HOST-nnn`) that are enforced by the policy decision point, the plugin host and the release or verification context, not by a provider. The kits list them as the cases a host must hold. They are not run in the open tree.
- **Extended** cases for negotiated capabilities, empty in 1.0.0 for most ports.

### Modes

The kit READMEs name three modes.

| Mode | Meaning | Where it can run |
| --- | --- | --- |
| Replay | Recorded or in-memory fixtures; no network, no live system | Anywhere. This is what the open tree implements |
| Live, publisher-run | The publisher runs the kit against the real system in an attested runner | Needs a real host, sandbox, egress proxy and broker |
| Live, registry-run | A registry runs the kit against the real system | Same needs. Not applicable to ports bound to a deployment, such as the sandbox provider |

The sandbox provider kit adds a rule that matters: a provider claims the `CONTAINER` or `GVISOR` isolation profile only after passing the live cases, and replay alone proves no isolation.

## The kits

| Kit | State in the tree | What it holds |
| --- | --- | --- |
| `knowledge/v1` | Runnable `knowledgekit`; runs CORE-001 to 005, 007, 008, 012 to 015 against any `Target`; tested on the sample provider | Seeded scopes `kit` and `other`; scope escape attempts; bounds |
| `scm/v1` | Runnable `scmkit`; CORE-001 to 010 against a `Target` and a publisher's `Subject`; also exports `ValidateRepository`, `ValidatePullRequest`, `ValidateStatus` for a host to apply to any provider | Pull request opened once, merge at the verified head, idempotent comment |
| `ciexecutor/v1` | Runnable `cikit`; CORE-001 to 008; exports `ValidateOperation` | A run started once under one key; dry run; cancel twice |
| `verifier/v1` | Runnable `verifierkit`; CORE-001, 002, 003, 005, 006, 008, 009, 010, 014; exports `ValidateResponse` | Clean, seeded and crashing candidates; suppression directives; fingerprints |
| `ticketing/v1` | Runnable `ticketingkit`; TICKETING-001 to 024 as a replay kit, proven against an in-memory fake | Identical not-found for hidden or foreign issues; body truncation; text stripping |
| `evidence/v1` | Data, not code: 285 vector directories and 228 golden exports with generated test keys | Any `evidence/v1` verifier must match each vector's exit code, level and finding codes |
| `authorexecutor/v1`, `evidencestore/v1`, `sandboxprovider/v1`, `transparencylog/v1` | README with the case table; no runnable Go kit in the tree | The list of cases a future kit must hold |

Some kit notes worth knowing:

- The **knowledge** kit puts a trap in every scope-related case: a document in scope `other` that matches the query must never be returned for scope `kit`, and encoded dot segments must be refused by the provider's own grammar.
- The **scm** kit's `Subject` is how a publisher supplies fixtures (an existing repository, a protected and an unprotected branch, a candidate branch, a moved branch, a pull request with checks and reviews). Its test runs against the replaying build of `scm-github`.
- The **ticketing** kit has no provider in the tree. Its test checks the kit itself: a conforming in-memory fake passes every case, and each of 37 fakes broken in a single way fails exactly the cases that guard that fault. A provider's own test builds a `Target` over its replay build and calls `ticketingkit.Run`.
- **TICKETING-024** (markup in comments) needs an `Observer`; without one the case is reported as skipped with the reason, not passed.

## Run the runnable kits

From the root of a `numinance-spec` checkout:

```bash title="Run every runnable kit and the official provider tests"
go test -count=1 ./conformance/... ./plugins/... ./sdk/go/plugin/...
```

## Using a kit with your provider

The pattern is the same for every runnable kit:

<Steps>
<Step>

### Adapt your provider to the kit's `Target`

Each kit defines a small interface of the port's verbs. A direct adapter calls your provider's server type with no host process. The kit judges only what comes back, so a real host dispatching `Invoke` can sit behind the same interface.

</Step>
<Step>

### Supply fixtures

A kit with a `Subject` (scm, ciexecutor, verifier) needs data you provide: an existing repository and a missing one, a protected branch, a clean and a seeded candidate. The README for each kit says what must be seeded.

</Step>
<Step>

### Call the kit's `Run` from a test

For example `knowledgekit.Run(t, target)`. Each case becomes a subtest named by its id.

</Step>
<Step>

### Keep the negative controls

The knowledge and ticketing tests include deliberately broken targets that must fail. Do the same for the rules you add; a kit that cannot fail is not a test.

</Step>
</Steps>

## What a pass does not mean

- It does not cover the cases the skeleton does not run. The READMEs list them, for example the knowledge kit's principals, 1 MiB document and unreachable-source cases, and the verifier kit's 1025-violation candidate and nested-sandbox cases.
- It does not run the host checks. Scope refusal before `Invoke`, digest and bound checks on responses, unknown-field rejection and egress against metadata and private addresses are enforced by the host. A host kit must hold them; the open tree does not run them.
- It does not mean a live system behaves. Replay fixtures are redacted recordings or hand-written data, and several are explicitly not recordings.
- It is not a security certification, an audit or an endorsement. It states compatibility with the spec at a version.

## Failure modes

| Symptom | Likely cause |
| --- | --- |
| A case fails with an error that names a reason | Your provider returned a different `Reason` than the table expects, for example `NOT_FOUND` where `INVALID_ARGUMENT` is required |
| A broken-target test passes | The kit lost a guard; investigate before trusting any pass |
| The `sdk/go/plugin` tests hang | The environment forbids Unix sockets |
| An evidence vector expected `exit 5` and you got `0` | You pinned keys that make the export `verified` rather than `self-consistent`; check the vector's `flags` |
