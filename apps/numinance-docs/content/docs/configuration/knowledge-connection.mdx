<ShortProductTruth>
  A KnowledgeConnection is an org-approved, read-only door to a wiki, ticket system or document store. It names the provider, the endpoint, whose authority a read runs under, the exact tools allowed and their hashes, and the budget. It holds no credential.
</ShortProductTruth>

## When to use it

Use a KnowledgeConnection when engineers keep the information a change needs outside the repository: design pages, runbooks, ticket history. The context resolver searches these sources and assembles a bundle for each stage. The connection is the only way it can do so, and the org is the only scope that can create one. For the end-to-end flow, see [connect knowledge](/docs/guides/connect-knowledge), [the context resolver](/docs/architecture/context-resolver) and [knowledge and MCP](/docs/integrations/knowledge-mcp).

## Scope and merge rules

KnowledgeConnection is org-scoped only. The loader refuses any `metadata.scope` other than `SCOPE_ORG`, and the profile context refuses one loaded below the org. A repository can only name a connection in its adapter selector (`ports.knowledge`) when the org has granted it; it cannot define its own.

Three fields carry the `FORBID` merge directive: `endpoint`, `auth` and `oauth`. Only the org sets them, since they decide where reads go and under which authority.

### The two auth modes

`KNOWLEDGE_AUTH_USER_DELEGATED` runs a search or fetch under the grant of the human who triggered the change. `KNOWLEDGE_AUTH_SERVICE_ACCOUNT` is for unattended runs. The schema notes that the broker issues a service-account handle only with an approval record, that its effective scope is the intersection of the account's grant and the policy's allowed spaces and projects, and that whether the first release allows it at all is an open design question. Prefer user-delegated until your policy says otherwise.

## Working example

```yaml title="schemas/examples/KnowledgeConnection/confluence-eng.yaml"
apiVersion: numinance.dev/v1
kind: KnowledgeConnection
metadata: {name: confluence-eng, scope: SCOPE_ORG}
spec:
  provider: dev.numinance.official/bridge-mcp
  endpoint: https://mcp.example.com/v1/mcp
  auth: KNOWLEDGE_AUTH_USER_DELEGATED
  pinned_tools:
    - {name: searchConfluenceUsingCql, hash: {value: "sha256:3f1a9c0e5b7d2a4f6e8c1b3d5a7f9e2c4b6d8a0f1e3c5b7d9a2f4e6c8b0d1a3f"}}
    - {name: getConfluencePage, hash: {value: "sha256:9b2d4f6a8c0e1b3d5f7a9c2e4b6d8f0a1c3e5b7d9f2a4c6e8b0d2f4a6c8e0b1d"}}
  read_only: true
  scope: [ENG, PAY]
  budgets: {calls_per_stage: 8, bytes_per_call: 65536}
  cache_ttl: 2592000s
```

<IllustrativeNote>
  `mcp.example.com` is a placeholder host and the two hashes are sample values from the schema examples. They are not a real server, and the tool names are only a plausible shape. Compute real hashes from the tool inventory your administrator approves.
</IllustrativeNote>

A second example in the same directory shows the OAuth variant, which replaces nothing about the read-only rule:

```yaml title="schemas/examples/KnowledgeConnection/confluence-oauth.yaml"
apiVersion: numinance.dev/v1
kind: KnowledgeConnection
metadata: {name: confluence-oauth, scope: SCOPE_ORG}
spec:
  provider: dev.numinance.official/bridge-mcp
  endpoint: https://mcp.example.com/v1/mcp
  auth: KNOWLEDGE_AUTH_USER_DELEGATED
  oauth: {client_id: "https://numinance.example.com/oauth/client.json"}
  pinned_tools:
    - {name: getConfluencePage, hash: {value: "sha256:9b2d4f6a8c0e1b3d5f7a9c2e4b6d8f0a1c3e5b7d9f2a4c6e8b0d2f4a6c8e0b1d"}}
  read_only: true
  scope: [ENG]
```

## How it behaves in the designed runtime

<DesignNote title="Pinning, quarantine and delivery">
  Tool pinning exists because a tool server's description can change after approval. The requested `pinned_tools` are only a request: the runtime trusts the administrator-approved pins recorded in the lockfile, not this file alone. On each tool listing the bridge compares the server's inventory with the pins, and any drift quarantines the connection until it is re-approved. Read-only is enforced in layers, not only by `read_only: true`.

  Retrieved text is untrusted. It is redacted before it is stored, delivered to the executor as a read-only copy, and labelled untrusted in prompts. It can inform a change; it cannot alter policy, tool lists or approvals. The enterprise server itself is never attached to the executor. See [context bundle](/docs/configuration/evals-and-context-bundle) for the record a read produces.
</DesignNote>

## Security implications

- No secrets in the file. There is no field for a token, and the schema is strict, so adding one is an error (shown below). The broker holds secrets and issues a handle. `extensions` must not hold credentials, endpoints, tool mappings or caps either.
- Pins are the trust boundary, not the endpoint. An https URL tells you the transport, not that the server is the one you approved.
- The endpoint rule excludes IP literals, single-label hosts and `.local`, `.internal` or `.localhost` suffixes, which narrows server-side request forgery, but the egress allow-list is the real control.
- `scope` is passed as a parameter, never as query text. Do not rely on it to hide documents the delegated user can already read.
- A passing `numi validate --files` does not check that a pin matches a real tool, that the host is allow-listed or that the provider is installed.
