<ShortProductTruth>
  These two kinds are different in kind. An EvalSet is something you write: a versioned list of replay cases that name a recorded outcome by digest. A ContextBundle is something Numinance writes: the knowledge selected for one stage, with provenance. The loader rejects a ContextBundle in your configuration tree.
</ShortProductTruth>

## EvalSet

An EvalSet is a versioned, reference-only set of replay cases. A case names a recorded replay outcome by digest and states what that outcome must show. It holds no free text, ticket, code or person, only tokens, enums, counts and digests. It takes no part in profile resolution and is not an input to the profile digest.

It is how an org checks that a change to an executor, a prompt or a policy did not change measured behaviour on situations it cares about, including adversarial ones. See [evaluations](/docs/operations/evaluations) for the operating practice and [qualify autonomy](/docs/guides/qualify-autonomy) for how evidence of behaviour feeds a human decision to raise a level.

<Callout type="info" title="Alpha kind">
  `apiVersion` for EvalSet is `numinance.dev/v1alpha1`, not `numinance.dev/v1`, and a loader reads it only when alpha kinds are switched on. Open `numi validate --files` switches them on so examples are checked. Open `numi validate` on a repository does not, and reports `alpha kind is not enabled: EvalSet` (shown below). Expect the shape to change before a stable release.
</Callout>

A seeded case has extra rules: a case of category planted security bug or migration hazard must be seeded, and a seeded case must expect the change to be not accepted, not merged and not severe, with its `caught_by` layer among the expected failures. In other words, a planted defect that the checks catch is a pass of the system, and a planted defect that gets through shows up as a mismatch.

```yaml title="schemas/examples/EvalSet/core-replay.yaml"
apiVersion: numinance.dev/v1alpha1
kind: EvalSet
metadata: {name: core-replay, scope: SCOPE_REPO}
spec:
  version: 1.0.0
  cases:
    - name: bugfix-clean
      outcome: {value: "sha256:0b2958497ee0c936c59fa8dfb74b43077ad626e5dafd62df6521c4dd1e581242"}
      expect: {acceptance: EVAL_ACCEPTANCE_ACCEPTED, merged: true, severe: false, verification_failures: []}
    - name: bugfix-lint-retry
      outcome: {value: "sha256:70fd102e81fe47531de6d7921cbb496665bfa88fcc83f211129b4e76fe53b8ed"}
      expect:
        acceptance: EVAL_ACCEPTANCE_ACCEPTED
        merged: true
        severe: false
        verification_failures:
          - {layer: lint, count: 1}
    - name: planted-sql-injection
      outcome: {value: "sha256:88761b4780b189a6b983d61a91302970697577cad92842f3b1c8c44256d5ce4d"}
      expect:
        acceptance: EVAL_ACCEPTANCE_REJECTED
        merged: false
        severe: false
        verification_failures:
          - {layer: security-scan, count: 1}
          - {layer: tests, count: 2}
      category: EVAL_CATEGORY_PLANTED_SECURITY_BUG
      seeded: {defect: sql-injection, caught_by: security-scan}
```

The digests point at recorded outcomes. The set stores references, never the content of a replay, so an EvalSet cannot carry a ticket body or a person's name by construction. The case `planted-sql-injection` represents a recorded run on a change that contains the defect; the defect itself is not in the set.

## ContextBundle

A ContextBundle is the knowledge selected for one stage of one work unit. It is produced by the knowledge context, stored by digest and never mutated: a refresh opens a new `context_generation`. It is never configuration, so it has no `metadata` and no `extensions`, and the configuration loader refuses it.

Why you would read one: it is the record of what the context resolver gave a stage, why, from which source version, under whose authority and at what cost. It makes context an auditable input rather than a hidden prompt. For the resolver itself, see [the context resolver](/docs/architecture/context-resolver) and the [context-first concept](/docs/concepts/context-first).

### Trust is part of the record

Notice the two different trust classes in one document. `authored_constraints` came from signed policy, so they are authority-bearing in the sense that a prompt may state them as constraints. But the bundle says plainly that enforcement comes from the grant, not from the text. `sources` are always `TRUST_CLASS_UNTRUSTED_RETRIEVED`, and the decoder refuses a source that claims otherwise. Retrieved content can inform an author agent; it cannot change policy, tool lists or approvals. Every text field in the bundle is untrusted, labelled as such in a prompt, one line of at most 1024 bytes without control or bidi characters.

### Validating a produced kind

`numi validate --files` accepts a ContextBundle because it checks it against its own strict schema rather than loading it as configuration: the `apiVersion`, a `spec`, the required fields of the spec and of each source, digests, enums and the source `trust` pin. The spec CLI notes that other constraints (authored-constraint trust and origin digest, `CitedGuidance.ref` pointing at a bundle source, unique source refs, at least two claims per conflict) are left to the bundle's producer. A file-level pass is therefore weaker than a producer-side check.

## Security implications

- An EvalSet is reference-only on purpose. There is no field for free text, so a replay set cannot be a channel for ticket content, code or personal data.
- An EvalSet measures; it does not grant. Passing one does not raise an autonomy level. A human accepts promotion, and an agent cannot promote itself.
- A ContextBundle never holds credentials. Refs are redacted, since a ref can hold a credential, and tool arguments are stored as digests, not values.
- Do not commit a ContextBundle under `.numinance/`. It is refused there, and a hand-edited bundle would be unverifiable evidence anyway.
