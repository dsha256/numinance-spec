# transparencylog conformance kit, v1

Skeleton. The acceptance tests for a provider of `numinance.ports.transparencylog.v1.TransparencyLogService` (`proto/numinance/ports/transparencylog/v1/transparencylog.proto`). The kit version tracks the port minor; this skeleton tracks 1.0.0. The runnable kit (replay fixtures, live kit, harness) is added by the plugin host work package; until then this file is the list of cases the kit must hold. Modes are those of ADR 0015: replay, live publisher-run in an attested runner, live registry-run.

The kit takes the log origin, public key and witness keys from its own configuration, never from the provider, and checks every note, entry and proof offline (C2SP signed note, RFC 6962 and RFC 9162 hashing, the strict decoder of the entry format). Nothing in the handshake declares the entry format: the kit learns it from its configuration and from the first AppendResponse, and every entry of one log origin must use that one format, so a later entry in another format fails the provider. The kit runs the Core cases once per format it holds and the provider serves; a format outside the three fails the provider. The anchoring key the kit signs with is generated by the kit for the run and is never a customer key. Live mode (publisher-run or registry-run) runs only when an environment variable set by the operator enables it; replay mode needs nothing.

Cases do not assume an empty log. The kit reads the starting checkpoint size `s0` (0 for a fresh log) and states every expectation relative to it: after three appends the size is at least `s0 + 3`, indexes are at least `s0`, and `min_tree_size` is `s0 + 3`. Other writers may append meanwhile, so sizes are lower bounds, never exact. CORE-001 runs only when the kit configuration says the log is fresh. "Bounds" means each listed input alone, every other field valid. Each Append in the kit carries a kit-generated deterministic (RFC 6979) signature and public key; numinance.leaf.v1 ignores them.

## Core

| Id | Verb | Case | Expect |
| --- | --- | --- | --- |
| CORE-001 | Checkpoint | a fresh log (kit configuration says so) | NOT_FOUND |
| CORE-002 | Append | three leaves of kind 0x48 and 0x41 | three distinct indexes, each at least `s0`; each `entry` is 1 to 65536 bytes with the declared `entry_format`; the decoder accepts it and it carries the appended leaf |
| CORE-003 | Append | a malformed leaf: 32 or 34 bytes; kind byte other than 0x48 and 0x41; for hashedrekord an absent, over-long (signature above 72 or key above 128 bytes) or wrong-key signature | INVALID_ARGUMENT for each; the next Checkpoint's size is unchanged by this call The refusal of a wrong-key signature is the log's (Rekor verifies on create), mapped to INVALID_ARGUMENT by the provider; a provider must not add its own signature check. |
| CORE-004 | Checkpoint | after CORE-002 | the note verifies against the configured origin and key; at most 16 signature lines and 65536 bytes; size at least `s0 + 3`; for a log with no other writer the root equals the root of the entries' leaf hashes |
| CORE-005 | Checkpoint | two checkpoints with an Append between them | the later has the larger size; the earlier note is byte-identical to what the log signed (not re-signed) |
| CORE-006 | Prove | each CORE-002 leaf with `min_tree_size` `s0 + 3` | the proof verifies against the returned checkpoint, whose size is at least `s0 + 3`; `proof.tree_size` equals the note's size and `proof.leaf_index` the request's; the `entry` carries the leaf |
| CORE-007 | Prove | `leaf_index` at or past the log's size; an index whose entry does not carry `leaf` | UNAVAILABLE for an index at or past the log's size (the caller's index may come from a primary this replica has not reached, so it is never definitely absent); NOT_FOUND for an index whose entry does not carry `leaf` |
| CORE-008 | Prove | `min_tree_size` above the log's size | UNAVAILABLE |
| CORE-009 | Prove | bounds: `leaf` of 32 or 34 bytes or a bad kind byte; `min_tree_size` 0 and 2^53; `leaf_index` 2^53-1 | INVALID_ARGUMENT for each |
| CORE-010 | Prove (consistency) | the sizes of the two checkpoints of CORE-005 | the proof verifies against both notes |
| CORE-011 | Prove (consistency) | equal sizes | the empty path |
| CORE-012 | Prove (consistency) | bounds: old size 0; old above new; a size of 2^53; a request naming no kind. Then `new_tree_size` above the log's size | INVALID_ARGUMENT for each bound; UNAVAILABLE for the size not yet served |
| CORE-013 | all reads | 1000 leaves, then Prove of every 97th leaf and a consistency Prove from every 97th size | every proof verifies and no path exceeds 64 entries |
| CORE-014 | Prove | the checkpoint a Prove returns, then the latest Checkpoint | a consistency Prove between their sizes verifies, so the Prove checkpoint is a prefix of the latest |
| CORE-015 | Append | the kit sends a second Append of the same leaf on purpose, modelling a caller whose `Lookup` answered NOT_FOUND or a caller of a provider without `transparencylog.lookup`, on a provider that does not declare `transparencylog.dedup`; the retry rule (record the received `leaf_index`, never re-append a recorded leaf, call `Lookup` first after an unknown outcome where `transparencylog.lookup` is declared) binds the caller, not the provider | a second Append is accepted and the tree grows by at least one unless the provider deduplicated, in which case the returned index is the first entry's; every entry carrying the leaf Proves; the kit never counts the second entry as a provider fault |

## Injected faults (replay harness)

The harness alters one provider answer; the kit's client must refuse it and report a provider fault.

| Id | Verb | Fault |
| --- | --- | --- |
| FAULT-001 | any note | a note over 65536 bytes, or with 17 signature lines |
| FAULT-002 | Append, Prove | an entry over 65536 bytes, or one that does not carry the leaf |
| FAULT-003 | Prove | a checkpoint of size below `min_tree_size` |
| FAULT-004 | Prove | `proof.tree_size` other than the note's size, or `proof.leaf_index` other than the request's |
| FAULT-005 | Checkpoint, Prove | a note whose origin or key is not in the kit's trust set |
| FAULT-006 | Prove (consistency) | a proof whose sizes differ from the request |
| FAULT-007 | Checkpoint | a note whose size is below that of the previous note the kit holds (the verifier, not the provider, catches a step back) |

## Entry format matrix

Each row is run with CORE-002, CORE-004, CORE-006 and CORE-010 (relative to `s0`) on a provider that serves the format. The kit holds one strict decoder per format; for every format a case also feeds the decoder an entry with a duplicate key or unknown field (where the encoding has keys) and an empty entry, and expects it to be refused.

| Id | Format | Append | Checkpoint | Prove | Prove (consistency) |
| --- | --- | --- | --- | --- | --- |
| FMT-001 | `numinance.leaf.v1` | `entry` is exactly the 33-byte leaf and nothing else | note signed by the customer-local ledger key, with the signing time in its extension line | entry equals the leaf; proof verifies | proof verifies |
| FMT-002 | `dev.sigstore.hashedrekord.v0_0_1.json` | `entry` is the Rekor v1 canonical-JSON body, built from the request's signature and key (a provider that signs on its own behalf fails); its public key is the anchoring key, the signature verifies, the hash algorithm is sha256 and the digest is that of `"numinance.evidence.v1.Anchor" \|\| sha256(leaf)` | the log's own signed note, never re-signed | entry carries the leaf's anchor digest; proof verifies | proof verifies |
| FMT-003 | `dev.sigstore.hashedrekord.v0_0_2` | the same four checks on the Rekor v2 encoding, built from the request's signature and key (a provider that signs on its own behalf fails) | the log's own signed note, never re-signed | the same as FMT-002; the index is a hint and the proof is computed from tiles | proof verifies |
| FMT-004 | any format outside the three | the kit refuses the response | not applicable | the kit refuses the response | not applicable |
| FMT-005 | `dev.sigstore.hashedrekord.*` | an entry signed by a key other than the anchoring key, or a signature over another leaf, or a hash algorithm other than sha256 | not applicable | the kit refuses the entry | not applicable |

## Extended

Run only when the provider declares the capability.

| Id | Capability | Case | Expect |
| --- | --- | --- | --- |
| EXT-001 | `transparencylog.lookup` | Lookup of each appended leaf; of an absent leaf | the index of the first entry carrying it, and Prove at that index verifies; on a shared log the verifier may refuse the entry at that index (a foreign entry), which is not a provider fault, and the kit falls back to the index Append returned; NOT_FOUND for the absent leaf |
| EXT-002 | `transparencylog.lookup` | bounds: `leaf` of 32 or 34 bytes; a kind byte other than 0x48 and 0x41 | INVALID_ARGUMENT for each |
| EXT-003 | `transparencylog.dedup` | a leaf already in the log appended again; 16 concurrent Appends of one new leaf | the index it holds; one index for all and the tree size grows by one |
| EXT-004 | `transparencylog.witness` | Checkpoint | the note carries at least one witness cosignature that verifies against a witness key from the kit's configuration |

A provider that does not declare `transparencylog.lookup` is not sent Lookup; a provider that serves it without declaring it fails the handshake check.

## Not covered by this kit

- Which leaves are appended, and when a per-Change checkpoint is taken, is the evidence context's rule, not the provider's.
- The last-held checkpoint per origin, trust on first use, the consistency check before an inclusion proof is accepted, and the fork handling that trips the circuit breaker are evidence-context duties. The kit checks only that the provider's proofs verify.
- Log time (a witness cosignature, an RFC 3161 timestamp, the local ledger's extension line) is verified by the evidence context; the kit checks the note, not a clock.
- Custody of the log key and of the anchoring key is a deployment property, not a protocol case.
