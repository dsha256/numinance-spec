## Cases with no data vector

Each is a case the generator does not emit, with the reason. A verifier covers each in its own tests.

- `too_many_records`: a chain of 32769 valid records is about 20 MB, and a fixture that loops over the whole range is refused by the repository test rules. The shipped verifier tests the bound at its edge with a lowered record limit. A verifier of this spec bounds the chain at 32768 records and tests the boundary with its own option.
- The check that the manifest's range and head are the attestation's (the third case of the manifest binding): the attestation is accepted only when its range and head equal what the chain derives, and the manifest is compared with the chain first, so a manifest that equals the chain while the attestation differs cannot exist. The check is subsumed by the attestation re-derivation.
- A chain whose next sequence would exceed 2^53-1: no file can reach it. A record that states such a sequence is `record_invalid` (vector `chain-sequence-above-2-53`).
- A file name of 256 bytes: file systems refuse names over 255 bytes, so no directory can hold one. A name with a control character is covered (`directory-refused-control-character-name`).
- A record line of exactly 3 MiB: the line limit and the record decoder limit are the same number, so no line at the edge can pass; a line one byte over is covered (`record-line-over-3-mib`).
- Exit codes 1, 6, 7 and 8: they depend on the environment (an internal error, never produced by verify, an I/O error, a deadline).
- Code points that Unicode assigns after the Go release in use: the printable-text rule follows the Unicode table of the Go release that built the verifier, so the vectors name code points that no release treats as printable (U+E000, U+0378, U+FFFF) and none at a boundary.
- Another file system naming the same bytes differently (case folding, normalisation): a verifier compares bytes.
