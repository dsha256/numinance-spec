# authorexecutor conformance kit, v1

Skeleton. The acceptance tests for a provider of `numinance.ports.authorexecutor.v1.AuthorExecutorService` (`proto/numinance/ports/authorexecutor/v1/authorexecutor.proto`). The kit version tracks the port minor; this skeleton tracks 1.0.0. The runnable kit (replay fixtures, live kit, harness) is added by the plugin host work package; until then this file is the list of cases the kit must hold. Modes are those of ADR 0015: replay, live publisher-run in an attested runner, live registry-run. Column "Mode": `all` runs in every mode; `live` needs a real sandbox, egress proxy and broker and runs in the two live modes only. A live case that expects a read, write or request to fail in the sandbox runs under the CONTAINER and GVISOR profiles; under PROCESS masked paths are absent from the worktree on disk, writes are refused at the candidate check (HOST-012), and egress is unrestricted and decided at PRIVILEGED (sandboxprovider port, Isolation and Paths; HOST-013).

Every case runs the adapter with its pinned ExecutorManifest inside a fresh work-unit sandbox, as an author-agent run, with fresh `change_id`, `work_unit_id`, `run_id` and `grant_id` values (prefix plus 32 lowercase hex characters) and a valid request built from the grant unless a case says otherwise. Tasks are scripted: the kit's task asks for a fixed change, so a case checks the stream's shape and the sandbox's state, never the quality of the work. "Bounds" below means each listed input alone, every other field valid. A stream "is valid" when it holds 1 to 1023 events, its first is EXECUTION_STARTED at sequence 1, its sequences are consecutive, its last and only its last is EXECUTION_COMPLETED or EXECUTION_FAILED, each message is at most 32 KiB serialized, and every `subject` and `references` entry follows the proto. "Rejected" means the status code named, with no event sent and no harness process started. The kit's canary secret is planted on the host before every live case.

Plan is a capability, not a Core verb (ADR 0046): an adapter that serves it claims `STRUCTURED_PLAN` in its `Capabilities` answer, and the host dispatches Plan only to an adapter that does (HOST-014). The Plan stream is a `PlanResponse` stream with the rules of Execute, and a FILE_CHANGED event breaks it.

Runnable now, in this repository: the stream half of PLAN-001 and PLAN-002 (the `PlanResponse` stream rule, with no FILE_CHANGED) and PLAN-003 (the request bounds) run offline as `authorexecutor.NewPlanRule` and `authorexecutor.ValidatePlanRequest` in `sdk/go/ports/authorexecutor` (`plan_rule_test.go`); the host wires the stream rule in the process provider. PLAN-003 covers only the shape listed in its row. The other bounds of CORE-018 that a planning request carries (the deadline, each budget field, the required digests and references other than `plan_ref`, `protected_resources`, the path grammar and the list bounds) are not checked by `ValidatePlanRequest` and are owed to the first adapter that serves Plan, which must apply them as CORE-018 does for Execute. Today the host dispatches a planning run through Execute, on the fake executor only (the claudecli adapter claims no `STRUCTURED_PLAN`); no code dispatches the Plan RPC and HOST-014 (the fail-closed refusal of an adapter without the capability) is owed with it. The live half of PLAN-002 (a harness that tries to write) needs a harness and is owed to the first executor adapter that serves Plan, together with the read-only worktree mount (ADR 0046, consequence 4).

## Host checks

These cases run against the host's request and stream validation with a scripted provider; they pin what every host does with a request and with a provider's answer. All run in every mode.

| Id | Case | Expect |
| --- | --- | --- |
| HOST-001 | first event not EXECUTION_STARTED; a sequence gap; a repeated sequence; an event after a terminal one; no terminal event; 1024 events; a message of 32 KiB plus 1 byte; EXECUTION_COMPLETED followed by a FAILED terminal Invoke message, or EXECUTION_FAILED by a SUCCEEDED one | the host rejects the stream and records the run as failed |

## Not covered by this kit

- How each ExecuteResponse crosses `PluginService.Invoke` (one RUNNING message each, a terminal message with no result) and the refusal of host-only references by ResolveReference are specified by plugin/v1. The reference checks are `plugin.StreamCheck`, `ports/authorexecutor.NewExecuteRule` and `plugin.CheckResolvable` in `sdk/go`. They cover HOST-001 in full except the ExecuteResponse bound on the wire and the deadline, and the `worktree_ref` and `network_policy_ref` refusal of HOST-010. The host must still add what needs its state, the HOST-002 subject, reference and diff checks, and the envelope rules listed in `sdk/go/plugin/doc.go`.
- Residency of the executor and model combination is validated at Change start from the live configuration (the residency design), not by a protocol case.
- The evidence record types of Execute are fixed with the execution context before the first spec tag; until then Execute declares no evidence.
- Harness-specific behavior (the CLI protocol, hooks, permission prompts) is each adapter's own test.
